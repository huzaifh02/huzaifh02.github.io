case-study/ecs-to-kubernetes-migration

Moving production from ECS and Cloud Run onto EKS and GKE without customer-visible downtime

Planned and ran the migration of production workloads from ECS to EKS and from Cloud Run to GKE, with Helm charts delivered from Git, a staged cutover, and a rollback path at every step.

Context

Production workloads ran on AWS ECS and GCP Cloud Run. Each platform had its own deploy scripts, its own configuration conventions and its own blind spots. Adding a service meant copying whatever the last one had done.

Problem

We needed one platform with consistent delivery, workload isolation, proper autoscaling and cluster-level observability, and we had to get there without customer-visible downtime on services that were already in production.

Constraints

  • Services could not be taken offline for a big-bang move.
  • Every step needed a way back that took minutes, not a redeploy from scratch.
  • Two clouds, so the pattern had to work on both EKS and GKE.

What I did

  1. Built the target platform first. EKS and GKE clusters, node pools, networking and IAM as reusable Terraform modules, with least-privilege IAM and Workload Identity Federation so no service-account keys exist.
  2. Standardised service manifests. A known-good Helm chart that each service starts from, with values per environment kept in a protected repo and applied with Helmfile. Dev, staging and prod are reconciled from Git, so drift gets corrected rather than discovered in the middle of an incident.
  3. Ran old and new side by side. Each service was deployed to Kubernetes while still live on ECS or Cloud Run, then validated with health checks, metrics and logs before any traffic moved.
  4. Staged cutover with rollback steps. Traffic shifted per service at the load balancer and DNS layer, with the old deployment kept warm. If error rates or latency moved, rollback meant pointing traffic back.
  5. Rebuilt delivery around the new platform. CI/CD moved to reusable GitHub Actions workflows with OIDC, image-existence checks before deploy, and deployment freeze windows (see the CI/CD platform case study).
  6. Added the platform features the old setup lacked. Taint-based node pool isolation, KEDA autoscaling on queue depth, and Prometheus/Grafana dashboards for CPU, memory, NAT, load-balancer health and subnet IP exhaustion.

Impact

  • No customer-visible downtime across the migration.
  • One delivery model across clouds. A new service starts from a chart rather than a copy-paste.
  • Environments stay consistent because Git is the source of truth, not whoever last ran kubectl.

What I would do differently

Put the observability stack on the new clusters before the first workload moves rather than alongside it. Having a baseline to compare against makes every cutover go/no-go decision faster.
