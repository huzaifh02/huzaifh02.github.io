1d:Taf6,<h2>Context</h2>
<p>Production workloads ran on AWS ECS and GCP Cloud Run. Each platform had its own deploy scripts, its own configuration conventions and its own blind spots. Adding a service meant copying whatever the last one had done.</p>
<h2>Problem</h2>
<p>We needed one platform with consistent delivery, workload isolation, proper autoscaling and cluster-level observability, and we had to get there <strong>without customer-visible downtime</strong> on services that were already in production.</p>
<h2>Constraints</h2>
<ul>
<li>Services could not be taken offline for a big-bang move.</li>
<li>Every step needed a way back that took minutes, not a redeploy from scratch.</li>
<li>Two clouds, so the pattern had to work on both EKS and GKE.</li>
</ul>
<h2>What I did</h2>
<ol>
<li><strong>Built the target platform first.</strong> EKS and GKE clusters, node pools, networking and IAM as reusable Terraform modules, with least-privilege IAM and Workload Identity Federation so no service-account keys exist.</li>
<li><strong>Standardised service manifests.</strong> A known-good Helm chart that each service starts from, with values per environment kept in a protected repo and applied with Helmfile. Dev, staging and prod are reconciled from Git, so drift gets corrected rather than discovered in the middle of an incident.</li>
<li><strong>Ran old and new side by side.</strong> Each service was deployed to Kubernetes while still live on ECS or Cloud Run, then validated with health checks, metrics and logs before any traffic moved.</li>
<li><strong>Staged cutover with rollback steps.</strong> Traffic shifted per service at the load balancer and DNS layer, with the old deployment kept warm. If error rates or latency moved, rollback meant pointing traffic back.</li>
<li><strong>Rebuilt delivery around the new platform.</strong> CI/CD moved to reusable GitHub Actions workflows with OIDC, image-existence checks before deploy, and deployment freeze windows (see the CI/CD platform case study).</li>
<li><strong>Added the platform features the old setup lacked.</strong> Taint-based node pool isolation, KEDA autoscaling on queue depth, and Prometheus/Grafana dashboards for CPU, memory, NAT, load-balancer health and subnet IP exhaustion.</li>
</ol>
<h2>Impact</h2>
<ul>
<li>No customer-visible downtime across the migration.</li>
<li>One delivery model across clouds. A new service starts from a chart rather than a copy-paste.</li>
<li>Environments stay consistent because Git is the source of truth, not whoever last ran <code>kubectl</code>.</li>
</ul>
<h2>What I would do differently</h2>
<p>Put the observability stack on the new clusters before the first workload moves rather than alongside it. Having a baseline to compare against makes every cutover go/no-go decision faster.</p>
