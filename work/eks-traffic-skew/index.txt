1e:Tdac,<h2>Context</h2>
<p>A backend service on EKS ran five identical replicas behind a ClusterIP Service. External traffic came in through an ALB and was balanced per request at Layer 7. Internal pod-to-pod traffic went through kube-proxy.</p>
<h2>Problem</h2>
<p>One pod sat at over 90% CPU while the other four idled under 5%. It looked like a capacity problem, so HPA did what it was configured to do. The deployment grew from 5 to 15 pods, the cluster autoscaler provisioned new EC2 nodes to fit them, and <strong>none of the new pods received a single request</strong>. The bill went up roughly threefold while the same pod kept throttling p99 latency.</p>
<p>Restarting the hot pod "fixed" it for a while, and then a different pod became hot. That was the first clue that this was a routing problem rather than a capacity problem.</p>
<h2>Root cause</h2>
<ul>
<li>kube-proxy in its default iptables mode picks a backend <strong>once per TCP connection</strong>, on the SYN packet, using random probability rules. It never sees individual HTTP requests.</li>
<li>Modern clients (Go <code>http.Client</code>, Node <code>undici</code>, Python <code>httpx</code>, Spring <code>WebClient</code>, gRPC) open a small pool of persistent connections at startup and reuse them indefinitely.</li>
<li>So the random pick at startup effectively becomes permanent. New replicas only get traffic when a new connection is opened, and existing clients were not opening any.</li>
<li>HPA averages CPU across replicas. One pod at 100% and four at 10% eventually pushes the average past the target, so it scales out capacity that can never be reached.</li>
</ul>
<h2>What I did</h2>
<ol>
<li><strong>Reproduced it on a live EKS cluster</strong> with a five-replica CPU-bound deployment, measured with Prometheus and Grafana. The hot pod ran at about 112 millicores while the four peers sat at about 0.1 millicores.</li>
<li><strong>Tier 1, application level:</strong> client-side connection recycling, reconnecting after a request threshold with jitter so every service does not reconnect at once. Each new handshake gives kube-proxy a chance to rebalance, and requests evened out to about 2,000 per pod.</li>
<li><strong>Tier 2, cluster level:</strong> for fleets where changing every client library is not realistic, switched kube-proxy to IPVS mode with the least-connection (<code>lc</code>) scheduler.</li>
<li><strong>Tier 3, platform level:</strong> for HTTP/2 and gRPC, Layer 4 balancing is not enough. Per-request routing goes through Gateway API or an internal Envoy that points at a <strong>headless Service</strong>. A normal ClusterIP returns one virtual IP, which would send everything back through kube-proxy and recreate the hot pod.</li>
</ol>
<pre><code class="language-yaml">apiVersion: kubeproxy.config.k8s.io/v1alpha1
kind: KubeProxyConfiguration
mode: "ipvs"
ipvs:
  scheduler: "lc"
</code></pre>
<h2>Impact</h2>
<ul>
<li>Traffic spread evenly across all five replicas, and CPU variance dropped to 2-5% with Layer 7 routing.</li>
<li>Autoscaling reacted to real demand again instead of to one saturated pod, so the idle nodes it had been adding went away.</li>
<li>The write-up became a public reference for a failure that is common and easy to misdiagnose.</li>
</ul>
<h2>What I would do differently</h2>
<p>Alert on skew directly. A per-deployment "max pod CPU divided by median pod CPU" ratio in Prometheus would have caught this before HPA did, and it is cheap to add to every deployment.</p>
