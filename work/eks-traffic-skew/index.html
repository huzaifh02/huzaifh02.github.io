One hot pod, four idle ones: fixing Kubernetes traffic skew on EKS

One replica pinned at 90%+ CPU while identical pods idled, and HPA scaling out made the bill worse without fixing it. Traced it to kube-proxy's Layer 4 routing combined with keep-alive connection pools, then fixed it at three levels.

Context

A backend service on EKS ran five identical replicas behind a ClusterIP Service. External traffic came in through an ALB and was balanced per request at Layer 7. Internal pod-to-pod traffic went through kube-proxy.

Problem

One pod sat at over 90% CPU while the other four idled under 5%. It looked like a capacity problem, so HPA did what it was configured to do. The deployment grew from 5 to 15 pods, the cluster autoscaler provisioned new EC2 nodes to fit them, and none of the new pods received a single request. The bill went up roughly threefold while the same pod kept throttling p99 latency.

Restarting the hot pod "fixed" it for a while, and then a different pod became hot. That was the first clue that this was a routing problem rather than a capacity problem.

Root cause

  • kube-proxy in its default iptables mode picks a backend once per TCP connection, on the SYN packet, using random probability rules. It never sees individual HTTP requests.
  • Modern clients (Go http.Client, Node undici, Python httpx, Spring WebClient, gRPC) open a small pool of persistent connections at startup and reuse them indefinitely.
  • So the random pick at startup effectively becomes permanent. New replicas only get traffic when a new connection is opened, and existing clients were not opening any.
  • HPA averages CPU across replicas. One pod at 100% and four at 10% eventually pushes the average past the target, so it scales out capacity that can never be reached.

What I did

  1. Reproduced it on a live EKS cluster with a five-replica CPU-bound deployment, measured with Prometheus and Grafana. The hot pod ran at about 112 millicores while the four peers sat at about 0.1 millicores.
  2. Tier 1, application level: client-side connection recycling, reconnecting after a request threshold with jitter so every service does not reconnect at once. Each new handshake gives kube-proxy a chance to rebalance, and requests evened out to about 2,000 per pod.
  3. Tier 2, cluster level: for fleets where changing every client library is not realistic, switched kube-proxy to IPVS mode with the least-connection (lc) scheduler.
  4. Tier 3, platform level: for HTTP/2 and gRPC, Layer 4 balancing is not enough. Per-request routing goes through Gateway API or an internal Envoy that points at a headless Service. A normal ClusterIP returns one virtual IP, which would send everything back through kube-proxy and recreate the hot pod.
apiVersion: kubeproxy.config.k8s.io/v1alpha1
kind: KubeProxyConfiguration
mode: "ipvs"
ipvs:
  scheduler: "lc"

Impact

  • Traffic spread evenly across all five replicas, and CPU variance dropped to 2-5% with Layer 7 routing.
  • Autoscaling reacted to real demand again instead of to one saturated pod, so the idle nodes it had been adding went away.
  • The write-up became a public reference for a failure that is common and easy to misdiagnose.

What I would do differently

Alert on skew directly. A per-deployment "max pod CPU divided by median pod CPU" ratio in Prometheus would have caught this before HPA did, and it is cheap to add to every deployment.
