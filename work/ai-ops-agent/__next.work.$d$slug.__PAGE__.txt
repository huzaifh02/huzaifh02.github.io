a:T139a,<h2>Context</h2>
<p>Much of a platform team's day goes on answering questions. Which subnet is that service in? Why did this cron job fail last night? Is staging on the new database yet? The answers exist in Terraform, Helm charts, cloud APIs and logs, but finding them takes context, so the question lands on a senior engineer and costs them twenty minutes plus whatever they were in the middle of.</p>
<h2>Problem</h2>
<p>The goal was to automate lookups and first-pass incident triage against <strong>real production accounts</strong>, across three AWS accounts and four GCP projects, without creating a new way to break production. A language model is non-deterministic, and a system prompt is a request, not a security control.</p>
<h2>Design principles</h2>
<ul>
<li><strong>The model sits inside a deterministic layer.</strong> Plain code with unit tests decides what reaches the model and what its tool calls are allowed to do.</li>
<li><strong>Credentials are the real boundary.</strong> Every guard above them can fail; the identity it runs as still cannot write, read secrets or decrypt data.</li>
<li><strong>The infra repo is the knowledge base.</strong> No RAG pipeline: the agent reads a local clone of the repo the way an engineer would, and its playbooks are markdown skills in that repo, so improving the agent is a pull request.</li>
</ul>
<h2>What I built</h2>
<ol>
<li><strong>Read-only identity on both clouds, with no keys.</strong> Cross-account STS roles on AWS and Workload Identity Federation on GCP, using a custom read-only role of about 170 permissions. Explicit denies cover S3 object reads, secret values and KMS decrypt, so even a fully hijacked session cannot read customer data.</li>
<li><strong>A command firewall in front of every shell call.</strong> A PreToolUse hook splits commands on shell separators, unwraps <code>bash -c</code>, backticks and command substitution, and checks each piece. Its test suite grew from 121 to <strong>313 cases</strong> over six rounds of adversarial review by other models (Codex and Gemini), each round trying to get a write or an exfiltration past it.</li>
<li><strong>A permissions audit that cut the tool surface.</strong> I found that the SDK's permissive mode made the allowed-tools list advisory rather than enforced, so the agent could reach far more than intended. I cut the tools it can see from <strong>183 to about 40</strong> and enforced the rest in hooks.</li>
<li><strong>A prompt-injection boundary.</strong> Only the current @-mention counts as a request. Slack threads, logs, files and tool output are treated as data, and Slack tokens are stripped from the agent's environment. That defense is probabilistic, which is why the credentials are what actually limit the damage.</li>
<li><strong>Cost-aware model routing.</strong> A small classifier model reads each new thread and sends security and IAM questions to the strongest model and everything else to a mid-tier one, locking the choice per thread. The routing config lives in Parameter Store and reloads without a redeploy.</li>
<li><strong>Evals seeded from real incidents.</strong> Past incidents are replayed against the agent. One replay showed the stronger model solving 0 of 3 cases in a class where the mid-tier model solved 3 of 3, which changed the routing rules.</li>
<li><strong>Production hardening.</strong> Channel and user allow-lists, per-thread budgets and turn limits, an append-only audit log of every tool call, source pinned to a protected branch, graceful drain on shutdown, CloudWatch cost and heartbeat alarms, and 90 dependency advisories cleared. The system prompt went from 18 KB to 8.6 KB and the image from 2.94 GB to 2.08 GB.</li>
<li><strong>A daily CVE sweep as a scheduled domain.</strong> It matches 10+ advisory feeds (CISA KEV, NVD, GHSA, EPSS, cloud bulletins) against live Inspector, EKS/GKE and Lambda inventory and posts ranked, owner-assigned findings. It surfaced real exposures, including 63 hosts for one CVE, and its daily reports became the team's vulnerability evidence.</li>
</ol>
<h2>Impact</h2>
<ul>
<li><strong>14 engineers</strong> used it over 316 conversations in its first months. About two-thirds of those were mine, which is normal for an internal tool's builder; in one later week, 10 people used it and 6 of them were outside the platform team.</li>
<li><strong>Another engineering team forked it</strong> as their own on-call bot.</li>
<li>It helped trace a production slowdown across every tenant to one deploy's query change, and that investigation became a runbook and a reusable agent skill.</li>
<li>A typical root-cause investigation, such as tracing a failed customer cron job through CloudTrail, costs well under a dollar in model usage.</li>
</ul>
<h2>What I would do differently</h2>
<p>Build the command firewall parser first and fuzz it from day one. It is the hardest code in the system, and almost none of the work was "AI work". It was identity, least privilege, input validation and audit.</p>
