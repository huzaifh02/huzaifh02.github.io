a:T95b,<h2>Context</h2>
<p>The team moved off Jenkins to GitHub Actions. Jenkins agents had kept warm Docker layer and dependency caches on disk, and GitHub-hosted runners start cold every time, so builds got slower after the migration.</p>
<p>Deploy logic had also been copied into every repository, so a fix to one pipeline did not reach the others.</p>
<h2>Problem</h2>
<ul>
<li>Slow, cache-cold builds on hosted runners.</li>
<li>Long-lived cloud credentials stored as CI secrets.</li>
<li>No shared guardrails: nothing stopped a deploy of an image that did not exist, a deploy during a freeze, or a half-cancelled rollout.</li>
</ul>
<h2>What I did</h2>
<ol>
<li><strong>Reusable workflows as the platform.</strong> One set of versioned workflows (build, scan, deploy, rollback) that every service calls with a few inputs. Fixes and new guardrails ship once and reach every repo.</li>
<li><strong>OIDC instead of keys.</strong> GitHub's OIDC token is exchanged for short-lived AWS and GCP credentials scoped per repo and environment, so there are no long-lived cloud keys in CI.</li>
<li><strong>Deploy guards.</strong> Input validation, image-existence checks before deploy, deployment freeze windows, cancellation handling and a rollback path in every workflow. One pipeline deploys to both AWS and GCP.</li>
<li><strong>Self-hosted runners with a shared cache.</strong> Runners built on the Docker-in-Docker pattern keep the build cache on the same host, which gives back the warm-cache behaviour Jenkins used to have.</li>
<li><strong>Security in the path.</strong> Trivy image scans and coverage gates run before anything reaches production.</li>
<li><strong>Local testing with <code>act</code></strong> so workflow changes get tested before they burn CI minutes (written up publicly).</li>
</ol>
<h2>Impact</h2>
<ul>
<li>Pipeline runtime cut by <strong>about 80%</strong> compared with GitHub-hosted runners.</li>
<li>No static cloud credentials in CI.</li>
<li>One place to change delivery behaviour for every service.</li>
<li>Deploying and rolling back are self-service, so developers no longer wait on the DevOps team.</li>
</ul>
<h2>What I would do differently</h2>
<p>Version the reusable workflows with tags from the start. Pinning callers to <code>main</code> early on meant a workflow change reached every repo at the same moment, which is exactly what a platform should avoid.</p>
