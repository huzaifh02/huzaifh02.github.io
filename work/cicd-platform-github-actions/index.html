A CI/CD platform on reusable GitHub Actions: OIDC, deploy guards, and 80% faster pipelines

Replaced Jenkins with a reusable GitHub Actions workflow platform shared by every service, with keyless OIDC auth, guarded deploys across AWS and GCP, and self-hosted runners that fixed the caching problem the migration had created.

Context

The team moved off Jenkins to GitHub Actions. Jenkins agents had kept warm Docker layer and dependency caches on disk, and GitHub-hosted runners start cold every time, so builds got slower after the migration.

Deploy logic had also been copied into every repository, so a fix to one pipeline did not reach the others.

Problem

  • Slow, cache-cold builds on hosted runners.
  • Long-lived cloud credentials stored as CI secrets.
  • No shared guardrails: nothing stopped a deploy of an image that did not exist, a deploy during a freeze, or a half-cancelled rollout.

What I did

  1. Reusable workflows as the platform. One set of versioned workflows (build, scan, deploy, rollback) that every service calls with a few inputs. Fixes and new guardrails ship once and reach every repo.
  2. OIDC instead of keys. GitHub's OIDC token is exchanged for short-lived AWS and GCP credentials scoped per repo and environment, so there are no long-lived cloud keys in CI.
  3. Deploy guards. Input validation, image-existence checks before deploy, deployment freeze windows, cancellation handling and a rollback path in every workflow. One pipeline deploys to both AWS and GCP.
  4. Self-hosted runners with a shared cache. Runners built on the Docker-in-Docker pattern keep the build cache on the same host, which gives back the warm-cache behaviour Jenkins used to have.
  5. Security in the path. Trivy image scans and coverage gates run before anything reaches production.
  6. Local testing with act so workflow changes get tested before they burn CI minutes (written up publicly).

Impact

  • Pipeline runtime cut by about 80% compared with GitHub-hosted runners.
  • No static cloud credentials in CI.
  • One place to change delivery behaviour for every service.
  • Deploying and rolling back are self-service, so developers no longer wait on the DevOps team.

What I would do differently

Version the reusable workflows with tags from the start. Pinning callers to main early on meant a workflow change reached every repo at the same moment, which is exactly what a platform should avoid.
