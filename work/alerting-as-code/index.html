610 alarms vs 81: rebuilding production alerting as code, then removing the noise

A newly built production account went live with 81 alarms where the old one had 610. I rebuilt coverage as code across CloudWatch, EventBridge, GuardDuty and Prometheus, added a Terraform guard that fails the plan when something is unmonitored, and then tuned the noise by replaying real alert history instead of guessing thresholds.

Context

A new production account had been built quickly as part of an account migration. When I compared it with the old account, it had 81 alarms, all on RabbitMQ, against 610 in the old one. Copying the old alarms one for one was not an option either: one of them produced about 85% of the alert channel's volume.

What I did

  1. Rebuilt coverage as code. EventBridge security rules and GuardDuty, queue-drain alarms, load-balancer and namespace-level pod, node and autoscaling-group alarms, and managed Prometheus with Alertmanager rules, all in Terraform. Log retention went from 30 to 365 days.
  2. Made missing alarms a failed plan. An alarm coverage registry makes terraform plan fail if any load balancer or host has no alarm, so coverage cannot quietly drift back down.
  3. Worked around CloudWatch's limits instead of accepting gaps. Alarms cannot use a service dimension, wildcards or SEARCH, so I built namespace-level alarms that never sit in INSUFFICIENT_DATA forever.
  4. Tuned thresholds against real history. I replayed the live alert history against candidate thresholds before changing anything. The latency alarm went from 556 fires in 14 days to 0 on a 7-day replay while still firing on real slowness, and a failed job now posts once with a 24-hour reminder instead of about 72 times.
  5. Routed by severity. Alerts from many Slack channels were merged into a few severity-routed ones, and a scheduled AI digest summarizes what is new, persisting and resolved twice a day.

Impact

  • Coverage parity with the old account, enforced at plan time, with zero uncovered load balancers or hosts.
  • Engineers trust pages again, because the ones that fire are real.
  • A ten-fold jump in the operations bill (about $130 a day) was traced along the way to a security tool loop auto-creating over 1,000 tickets, and fixed.

What I would do differently

Define a handful of service-level objectives first and derive the paging alerts from them. Replaying history fixed the noise, but SLOs would have told us which of the 610 alarms deserved to page anyone at all.
